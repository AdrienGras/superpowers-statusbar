## Décisions (prises avec Adrien)

### #5 : menu de fin

Aujourd'hui, la fin de tour qui suit une réponse au menu clôt le run (`isMenuAnswered` puis `turnEnded` dans `src/reduce.ts`). Nouvelle règle :

- Le run ne se clôt que sur un signal explicite de choix :
  - les commandes déjà reconnues (`git merge`, `git push`, `gh pr create`, `git branch -D` : `branch-finished`) ;
  - ou, sur une fin de tour de la boucle principale en `finishing` après une réponse au menu, une réponse du modèle qui annonce que la branche est gardée : la phrase du skill `Keeping branch` (voir le marqueur `finishing.keep` et le `Report:` du skill), ou son équivalent français (garder ou conserver la branche). La regex exacte est laissée au builder. Elle doit rester étroite, bilingue et testée dans les deux langues.
- Sans signal, le run reste en `finishing` et l'attente devient `other` (bande ` WAITING · your turn `), sans notification. Le premier passage au menu reste `finishing-menu` avec sa notification.
- Conséquences : la confirmation `discard` attend que la personne tape `discard`, puis `git branch -D` clôt le run. Une réponse comme « corrige les tests » laisse le run ouvert.
- Pour ça, `turn-ended` porte la réponse du tour (`answer`, que l'événement `turn-end` a déjà).
- Cas connu, accepté : sur HEAD détachée, le skill ne prescrit pas de phrase pour « Keep as-is ». Le run reste alors en `your turn`, ce qui est vrai.

### #6 : skills appelés dans un subagent

- `hooks/normalize.ts` garde l'`agentId` des événements `skill`, et `stage-entered` le porte jusqu'au reducer.
- Un skill vu dans un subagent :
  - ne crée jamais de nouveau run et ne fait jamais reculer l'étape (pas de remise à zéro, même depuis `done`) ;
  - fait avancer l'étape, avec le mode qu'il apporte, seulement si le subagent n'a pas de rôle reconnu (`implementer`, `reviewer`, `re-reviewer`, `final-reviewer`, `builder-check`). Un agent de rôle `other` ou `unknown`, ou inconnu du run, peut faire avancer l'étape : c'est le cas de l'orchestrateur du mode « cheaper orchestration » de superpowers, qui appelle lui-même `subagent-driven-development` puis `finishing-a-development-branch` ;
  - dans un subagent au rôle reconnu, il est ignoré.
- Sans run en cours, un orchestrateur reste rattrapé par le script `sdd-workspace`, vu aussi dans les subagents, comme aujourd'hui.
- *(Décidé par Adrien après la relecture)* Un run `done` compte comme « pas de run en cours » pour `sdd-workspace`. Ce script, vu dans la boucle principale ou dans un subagent, démarre alors un nouveau run en `exec`, comme le fait déjà un skill d'étape après un run terminé. Sans cette règle, le plan d'un second run (lancé par exemple par un orchestrateur) se déverserait dans le résumé `done` du premier.
- Les skills de la boucle principale gardent la règle actuelle.

### #3 : RED/GREEN en mode inline

- On renforce la description de `report_phase` (`src/instrument.ts`) : elle dit explicitement que le contrôleur qui exécute lui-même un plan (`executing-plans`) signale `red`, `green` et `refactor` pour chaque tâche, comme un implementer.
- Pas de déduction depuis les lancements de tests : elle produirait des phases fausses (anti-objectif).
- L'avertissement e2e « pas de RED puis GREEN inline » reste un avertissement. Le run e2e de fin de session montre si la description a suffi. Si ce n'est pas le cas, #3 reste ouvert et la PR le dit (pas de `Closes #3`).

### #4 : skills tapés en `/superpowers:…`

- Source : le hook `command.run`, qui se déclenche pour chaque commande slash avec son nom résolu (`superpowers:brainstorming`). Ce nom passe par la même règle que l'outil `Skill` (`skillUsed` du détecteur : préfixe `superpowers:` retiré, puis table `SKILL_STAGES`), comme un skill de la boucle principale. Le hook laisse la commande s'exécuter normalement. Le hook existant sur `sp-progress` reste tel quel.
- Inconnue : le plugin de sécurité contourne peut-être aussi `command.run` pour un mod utilisateur. **Sonde autorisée** : un `claude -p "/superpowers:brainstorming …"` avec le mod chargé par `--plugin-dir`, `SP_STATUSBAR_TRACE` pointé sur un fichier, le modèle `haiku` et la même isolation que l'e2e (`--setting-sources project,local`). On regarde si la trace contient l'entrée en brainstorming.
- Si la sonde montre que `command.run` est contourné, le hook est retiré. La limite connue du README reste en place, #4 reste ouvert, et la PR le dit. Sinon, le README et la spec retirent la limite connue.

### #7 : `agent.spawn`

- `agent.spawn` devient la source du **départ** de tous les dispatchs, synchrones comme en arrière-plan. Le hook appelle `next(e)` pour obtenir l'`agentId`, puis observe un nouvel événement (description, prompt, `background`, `parentAgentId`, `agentId`). Le rôle se déduit des mêmes règles que le `tool.call` `Agent` aujourd'hui (`roleOf`). L'agent est en cours dès son départ.
- Les spawns de workflows (`workflow`) et de teammates (`isTeammate`) sont ignorés.
- Le `tool.call` `Agent` sert ensuite :
  - à récupérer la réponse d'un dispatch synchrone (`status: completed`) ;
  - de **repli** quand l'`agentId` n'a pas été vu au spawn *(mon choix)*. Le dispatch y est alors traité comme aujourd'hui. C'est ce qui couvre la reconstruction sur `--resume`, dont le transcript ne contient pas de spawn, ainsi qu'un spawn que le moteur ne nous aurait pas montré.
- Dédoublonnage par `agentId` : un dispatch n'est jamais compté deux fois (pas de deuxième `writing` ni `review` dans le trail, pas de fix round en double).
- La spec retire « `agent.spawn` n'est pas utilisé » et décrit la nouvelle répartition.

## Précisions sur les tickets de correction (mes choix)

- **#2** : tant que le plan n'est pas chargé (`isPlanLoaded` faux), le bloc ESTIMATE du pane n'est pas affiché (`estimate` renvoie `undefined`).
- **#8** :
  - `RM_WORKSPACE` reconnaît `rm -rf "$WS"`, `rm -r -f`, etc., et ne compte que le chemin du workspace du run (`s.workspace`). Une variable shell non résolue ne peut pas être comparée : elle n'est acceptée que si la commande l'a affectée au workspace du run, sinon elle est ignorée. La façon de faire est laissée au builder, l'anti-objectif tranche en cas de doute.
  - La règle Skill → skill dupliquée entre `src/rebuild.ts` et `hooks/normalize.ts` est factorisée dans `src/`.
  - `currentTask` classe par dernière activation.
  - Les phases TDD ne passent par l'`agentId` que pour un agent `implementer`.
  - Le jalon du nombre de tâches est repéré autrement que par une regex sur son libellé.
- **#9** : l'ouverture automatique du pane demande, en plus du plein écran, une largeur suffisante : 110 colonnes, le seuil à partir duquel le moteur ancre un pane à côté du transcript. La valeur est notée dans la spec.
- **#7** : un agent lancé qui ne rend jamais de rapport finit quand même : `turn.complete` se déclenche aussi sur `aborted` et `error`, donc aucun traitement en plus.
- **#10** : la bande du plan affiche le nombre de tâches dès qu'il est connu, puis la phase signalée : `plan · 12 tasks · self-review`. Le libellé de bande `plan self-review` devient `self-review`, puisque l'étape est déjà nommée. Le pane garde ses libellés. La bande final-review et finishing est réduite comme celle d'exec : le temps écoulé disparaît d'abord. Sous 10 colonnes, le bloc d'attente est tronqué à `columns`.
- **#15** : `author` dans `plugin.json` (Adrien Gras), `description` dans `marketplace.json` (celle du plugin). La ligne « Objectifs » de la spec dit que la reconstruction ne se fait que sur `--resume`. La section d'installation du README est vérifiée contre le dépôt maintenant que #1 est mergée.
